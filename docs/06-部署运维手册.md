# 企业级知识库部署运维手册

> 适用架构：TypeScript/NestJS 主服务 + Python/FastAPI 解析 Worker  
> 部署路径：Mac Docker Compose 验证 → Linux 单机 Compose → 按容量拆分服务

公开 API 的认证、capability/ACL、端点目录、错误码和安全调用示例见 [07-API使用说明.md](./07-API使用说明.md)；本文只负责部署、配置、监控和运维边界。

---

## 1. 部署拓扑

### 1.1 Mac 本地

```text
localhost
├── api:3000              NestJS 主服务
├── parser-worker:8000    仅 Compose 内网访问
├── redis:6379            任务队列
├── chroma:8000           向量库服务
└── postgres:5432         元数据与任务状态，默认仅 Compose 内网访问
```

只有 API 主服务映射到宿主机；其他服务默认不映射公网端口。调试时如需临时映射，应只绑定 `127.0.0.1`。本地 DBeaver 调试使用仓库的 `compose.db-gui.yaml`，将 PostgreSQL 映射为 `127.0.0.1:15432 → postgres:5432`；生产环境不得加载该覆盖文件。

### 1.2 Linux 单机服务器

```text
Internet
   │ HTTPS
   ▼
Nginx/Caddy
   │
   ▼
NestJS API ── Redis ── Ingestion Consumer
   │                        │
   │                        ▼
   │                   Python Parser Worker
   ├── PostgreSQL
   ├── Chroma
   └── Cloud Model APIs
```

所有内部服务位于私有 Docker network。Python Worker、Redis、PostgreSQL 和 Chroma 不直接暴露公网。

## 2. 环境要求

### 2.1 Mac 开发机

- Apple Silicon M1 Pro，16GB RAM。
- Docker Desktop 或兼容容器运行时。
- Node.js LTS、pnpm。
- Python 3.11（仅本地直接调试 Worker 时需要）。
- 建议预留 30GB 以上磁盘。

### 2.2 初期服务器

LLM 与可选 Rerank 使用云端 API；Embedding 也可使用本机 Ollama，因此起步不需要 GPU，但本机 Embedding 会占用开发机 CPU/内存：

- Linux x86_64 或 ARM64。
- 4 vCPU。
- 8–16GB RAM。
- 100GB 以上 SSD，按原始文档和向量规模调整。
- 固定出网、TLS 域名、备份存储。

OCR、LibreOffice 和大 PDF 解析会产生瞬时 CPU/内存压力。解析 Worker 并发从 1 开始，压测后再增加。

## 3. 镜像设计

### 3.1 TypeScript API Dockerfile

```dockerfile
FROM node:22-slim AS deps
WORKDIR /app
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY apps/api/package.json apps/api/package.json
COPY packages/contracts/package.json packages/contracts/package.json
RUN corepack enable && pnpm install --frozen-lockfile

FROM deps AS build
COPY . .
RUN pnpm --filter api build

FROM node:22-slim AS runtime
ENV NODE_ENV=production
WORKDIR /app
RUN groupadd --gid 10001 app && useradd --uid 10001 --gid app --create-home app
COPY --from=build --chown=app:app /app/apps/api/dist ./dist
COPY --from=build --chown=app:app /app/node_modules ./node_modules
COPY --from=build --chown=app:app /app/package.json ./package.json
USER app
EXPOSE 3000
CMD ["node", "dist/main.js"]
```

实际 Node 版本以项目 lock 和 CI 验证版本为准。构建前确认 workspace 产物路径，避免机械照抄。

### 3.2 Python Worker Dockerfile

```dockerfile
FROM python:3.11-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

RUN apt-get update && apt-get install -y --no-install-recommends \
    default-jre-headless \
    libreoffice \
    poppler-utils \
    tesseract-ocr \
    tesseract-ocr-chi-sim \
    libmagic1 \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app
COPY apps/parser-worker/pyproject.toml ./
COPY apps/parser-worker/requirements.lock ./
RUN pip install --no-cache-dir -r requirements.lock
COPY apps/parser-worker/app ./app

RUN useradd --uid 10002 --create-home worker \
    && mkdir -p /data/raw-docs /tmp/parser \
    && chown -R worker:worker /app /tmp/parser
USER worker

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "1"]
```

解析 Worker 初期使用一个进程。多个进程会分别加载 OCR 模型，可能迅速耗尽 16GB 内存。

## 4. Docker Compose

以下是结构示例，镜像 tag、Chroma 启动参数和 PostgreSQL/Redis 版本应在实施时查阅官方文档并固定具体版本，禁止生产使用浮动 `latest`。

```yaml
services:
  api:
    build:
      context: .
      dockerfile: apps/api/Dockerfile
    restart: unless-stopped
    env_file: .env
    ports:
      - '127.0.0.1:3000:3000'
    volumes:
      - raw_docs:/data/raw-docs
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
      chroma:
        condition: service_healthy
      parser-worker:
        condition: service_healthy
    healthcheck:
      test:
        [
          'CMD',
          'node',
          '-e',
          "fetch('http://127.0.0.1:3000/health/live').then(r=>{if(!r.ok)process.exit(1)})",
        ]
      interval: 30s
      timeout: 5s
      retries: 3
    security_opt:
      - no-new-privileges:true

  parser-worker:
    build:
      context: .
      dockerfile: apps/parser-worker/Dockerfile
    restart: unless-stopped
    env_file: .env
    expose:
      - '8000'
    volumes:
      - raw_docs:/data/raw-docs:ro
    tmpfs:
      - /tmp:size=1g,mode=1777,uid=10002,gid=10002
    healthcheck:
      test:
        [
          'CMD',
          'python',
          '-c',
          "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health/live')",
        ]
      interval: 30s
      timeout: 5s
      retries: 3
    security_opt:
      - no-new-privileges:true

  postgres:
    image: postgres:固定版本
    restart: unless-stopped
    environment:
      POSTGRES_USER: kb
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: kb
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U kb -d kb']
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    image: redis:固定版本
    restart: unless-stopped
    command: ['redis-server', '--appendonly', 'yes']
    volumes:
      - redis_data:/data
    healthcheck:
      test: ['CMD', 'redis-cli', 'ping']
      interval: 10s
      timeout: 3s
      retries: 5

  chroma:
    image: chromadb/chroma:固定版本
    restart: unless-stopped
    volumes:
      - chroma_data:/chroma/chroma
    expose:
      - '8000'
    healthcheck:
      test: ['CMD', 'bash', '-c', '</dev/tcp/127.0.0.1/8000']
      interval: 30s
      timeout: 5s
      retries: 5

volumes:
  raw_docs:
  postgres_data:
  redis_data:
  chroma_data:
```

不要把 `固定版本` 原样用于运行；实施时替换为已验证的精确 tag。

## 5. 本地启动

### 5.1 首次启动

DWG 转换在本地默认开启。先创建下面的 `.env`，再按照根目录 [README](../README.md) 的“项目启动顺序”准备经批准的 ODA Linux x64 Debian 包、构建 DWG 专用 Worker，并把容器内实际 ODA 版本填入 `DWG_CONVERTER_RELEASE`。基础 Worker 镜像不含 ODA，不能作为默认启动路径。

```bash
# 先打开 Docker Desktop，等待 Docker Engine 就绪
docker info
docker compose version
cp .env.example .env
# 编辑 .env，填写实际 ODA 版本、一个 Embedding Provider 和一个 LLM Provider
docker compose -f compose.yaml -f compose.dwg.yaml build parser-worker
docker compose -f compose.yaml -f compose.dwg.yaml config --quiet
docker compose -f compose.yaml -f compose.dwg.yaml up -d --build
docker compose -f compose.yaml -f compose.dwg.yaml ps
```

`docker compose build`、`run` 和 `up` 都要求 Docker Engine 已运行。只安装但没有打开 Docker Desktop 时，必须先启动 Docker Desktop，不能把连接 Docker daemon 失败误判为 Worker 构建错误。显式 `build parser-worker` 用于提前暴露 ODA 安装包、版本或镜像构建问题；`config --quiet` 校验 `compose.yaml + compose.dwg.yaml` 的合并结果；`up -d --build` 会复用已有构建缓存，并同步构建其他需要更新的服务。

本地需要同时保留 DBeaver 端口时，在 `config`、`up` 和 `ps` 命令中追加 `-f compose.db-gui.yaml`。生产环境不得加载该覆盖文件。

验证：

```bash
curl http://127.0.0.1:3000/health/live
curl http://127.0.0.1:3000/health/ready
```

查看日志：

```bash
docker compose -f compose.yaml -f compose.dwg.yaml logs -f api
docker compose -f compose.yaml -f compose.dwg.yaml logs -f parser-worker
```

停止但保留数据：

```bash
docker compose -f compose.yaml -f compose.dwg.yaml down
```

`docker compose down -v` 会删除 volumes，不得作为普通停止命令使用。

### 5.2 本地调试

需要直接运行主服务时，可让 Redis、PostgreSQL、Chroma 和 Worker 继续在容器中运行，并将这些端口只映射到 `127.0.0.1`。本机 `.env.local` 使用 localhost 地址，容器 `.env` 使用 service name。

### 5.3 `.env` 配置重载

环境变量在容器创建时读取。仅修改 `.env` 不需要重新构建镜像，但必须重建读取了该变量的容器：

| 配置范围 | 重建服务 | 命令/说明 |
| --- | --- | --- |
| LLM、Embedding、Rerank、查询、认证、ACL、主服务日志 | `api` | `docker compose -f compose.yaml -f compose.dwg.yaml up -d --force-recreate api` |
| Parser 资源限制、CAD/DWG、解析临时目录 | `parser-worker` | `docker compose -f compose.yaml -f compose.dwg.yaml up -d --force-recreate parser-worker` |
| `PARSER_INTERNAL_TOKEN` | `api parser-worker` | 两端使用同一新值并在一次命令中同时重建 |
| PostgreSQL 初始化账号、数据库和密码 | 特殊处理 | 已有 volume 时不能靠重建修改，按下述规则操作 |

API Key、模型名、超时和限流等运行配置变化不要求 `build`。源代码、锁定依赖、Dockerfile、Worker 系统依赖或 ODA 安装包变化才需要 `up -d --build <service>` 或显式 `build parser-worker`。重建后必须检查 `ps`、`/health/ready` 和相关服务日志。

`POSTGRES_USER`、`POSTGRES_DB` 和 `POSTGRES_PASSWORD` 是官方 PostgreSQL 镜像的初始化变量，只在空 `postgres_data` volume 首次启动时创建角色和数据库。已有 volume 时，`--force-recreate postgres` 不会修改数据库内部密码或重命名数据库。密码轮换应在受控维护窗口内完成：

1. 备份并确认当前数据库可恢复。
2. 在 PostgreSQL 内执行角色密码变更，不把新密码写入 shell 历史或日志。
3. 同步更新 `.env` 的 `POSTGRES_PASSWORD` 与 `DATABASE_URL`。
4. 重建 API 并验证 ready。

不得用 `docker compose down -v` 作为配置重载方式。Embedding Provider、模型、维度、关键分块或脱敏配置变化还需要新 collection 和索引迁移；重建 API 只会让新进程读取配置，不会自动证明旧索引兼容。

### 5.4 使用 DBeaver 只读查看 PostgreSQL

仓库的 `compose.db-gui.yaml` 仅用于本地调试：它把 PostgreSQL 加入现有 `edge` 网络，并仅绑定 Mac 回环地址 `127.0.0.1:15432`。启动数据库调试端口：

```bash
docker compose \
  -f compose.yaml \
  -f compose.dwg.yaml \
  -f compose.db-gui.yaml \
  up -d postgres
```

DBeaver 使用 PostgreSQL 驱动，连接参数为：

```text
Host:     127.0.0.1
Port:     15432
Database: POSTGRES_DB（默认 kb）
Username: POSTGRES_USER（默认 kb）
Password: POSTGRES_PASSWORD
```

连接后通过 `kb → public → 表` 查看 `Document`、`DocumentVersion`、`IngestionJob`、`KnowledgeChunk`、`QueryAudit`、`UserDirectoryEntry` 等元数据。向量属于 Chroma，不在 PostgreSQL 中。调试连接建议设为只读；不得用 GUI 绕过 API 的 tenant、ACL、状态机、审计和删除流程直接修改业务数据。DB Browser for SQLite 与 NoSQLBooster for MongoDB 不支持本项目的 PostgreSQL。

整套服务需要持续开放 DBeaver 端口时，后续 Compose 命令应继续加载同一覆盖文件。结束调试并移除端口映射：

```bash
docker compose -f compose.yaml -f compose.dwg.yaml \
  up -d --force-recreate postgres
```

该命令保留 `postgres_data` volume，只移除宿主机映射。生产部署禁止加载 `compose.db-gui.yaml`，PostgreSQL 仍应只位于私有 Docker network。

## 6. 健康检查

### `/health/live`

只确认进程事件循环正常，不调用外部付费模型。

### `/health/ready`

确认：

- 配置已通过校验。
- PostgreSQL 可连接。
- Redis 可连接。
- Chroma 可连接且 collection 指纹兼容。
- Python Worker 可连接。
- 必要目录可读写。

ready 不应每次实际调用云端模型，以免产生费用和触发限流。云端 Provider 使用独立、低频的合成监控。

分块与出网策略配置：

- `CHUNK_MAX_TOKENS` 与 `CHUNK_OVERLAP_TOKENS` 控制本地预处理预算。
- `REDACTION_POLICY_VERSION` 标识脱敏规则版本。
- `BUSINESS_REDACTION_RULES_JSON` 只接受受控的业务正则数组，不应包含真实客户数据。
- `ALLOW_CONFIDENTIAL_TO_CLOUD` 默认必须为 `false`。
- `CLOUD_EGRESS_RULES_JSON` 可按 sensitivity、Provider 和区域配置经过审批的精确规则。
- 受控 `ollama/local` 仅用于本机 Embedding，不属于云端出网；显式阻止规则仍可关闭它。云端 LLM 和 Rerank 对 confidential 的限制不因此放宽。
- `DWG_CONVERSION_ENABLED=true` 是本地默认值，并要求以 `compose.dwg.yaml` 构建的 Worker 和经过批准的 ODA Debian 包。Worker readiness 必须报告 `dwgConverter.status=up`；未就绪时不能把它作为普通格式解析继续运行。

修改关键分块或脱敏配置后，已生成 chunk 视为旧策略产物。进入向量阶段后必须建立新 collection 并重建，不得在旧向量空间中混写。

Embedding Provider 配置：

- `EMBEDDING_PROVIDER=none` 是默认值，本地基础设施启动不要求付费 Key。
- 选择 `alibaba` 时必须设置 `EMBEDDING_MODEL=text-embedding-v4`、允许的维度、区域、`DASHSCOPE_API_KEY` 和 HTTPS `ALIBABA_BASE_URL`。
- 选择 `ollama` 时不填写 Embedding API Key，必须设置 `EMBEDDING_MODEL`、维度、 `EMBEDDING_REGION=local` 和 `OLLAMA_BASE_URL=http://host.docker.internal:11434`。Docker Desktop 下 API 容器通过该地址访问宿主机 Ollama；schema 只接受该地址或 Compose 内的 `http://ollama:11434`，避免误发到任意 HTTP 服务。
- 使用本机 `bge-m3:latest` 时设置 `EMBEDDING_DIMENSIONS=1024`；文档与查询必须保留同一 Provider、模型和维度。
- `EMBEDDING_BATCH_SIZE` 当前不得超过官方同步接口限制 10。
- `EMBEDDING_REQUEST_TIMEOUT_MS`、`EMBEDDING_MAX_ATTEMPTS` 和 `EMBEDDING_RETRY_BASE_DELAY_MS` 控制超时与重试。
- Key 和 base URL 具有区域属性，生产配置前必须确认数据区域与合规审批。

付费 Provider 冒烟测试默认关闭。只允许使用专用测试 Key、脱敏合成输入并显式设置 `RUN_PAID_PROVIDER_TESTS=true`；普通 CI 不得调用付费服务。

阶段 14 真实质量评测同样属于付费、受控数据出网操作。运行前必须确认数据集已获批准、confidential 策略没有被绕过、使用专用测试 Key，并隔离其他流量。真实问题、标准答案、身份 profile 和原始 run 保存在 Git 忽略目录，不进入 CI artifact 或普通日志。先按 Vector Top 5 生成基线，再用相同数据集运行 Vector Top 20 + Rerank Top 5。两轮均通过 `quality:capture` 串行调用正式查询链路；命令要求显式设置 `RUN_PAID_PROVIDER_TESTS=true`，校验应用配置与 variant 一致，只保存来源引用和 trace ID。随后按 trace ID 从本次 Provider 用量记录归属实际单次成本，最后执行：

```bash
pnpm --filter @nexus-kb/api quality:evaluate -- \
  --dataset evaluation/private/dataset.json \
  --baseline evaluation/private/vector-top-5.run.json \
  --rerank evaluation/private/vector-top-20-rerank-top-5.run.json \
  --output evaluation/results/report.json
```

聚合报告不含问题或回答正文。`unauthorizedLeakRate` 必须为 0，`costCoverage` 必须为 1；否则不得依据质量增益启用 Rerank。数据集、身份 profile 和原始 run 权限必须为 0600 或更严格。报告阈值、Provider 账单价格和数据集版本必须随评测结果一并归档到受控系统。

LLM 与 Rerank Provider 配置：

- `LLM_PROVIDER` 支持 `none | openai | google | deepseek | alibaba | custom`。选择非 `none` 时必须同时配置对应 API Key、HTTPS base URL 和 `LLM_MODEL`。
- `LLM_FALLBACK_PROVIDER` 默认 `none`。启用时必须配置独立的 `LLM_FALLBACK_MODEL`；只有 primary 的 rate limit、timeout、network 或可重试 5xx 才会切换，认证和参数错误失败关闭。
- `LLM_TEMPERATURE`、`LLM_MAX_OUTPUT_TOKENS`、`LLM_REQUEST_TIMEOUT_MS`、 `LLM_MAX_ATTEMPTS` 和 `LLM_RETRY_BASE_DELAY_MS` 控制生成与重试。模型是否支持特定生成参数应在上线前用该模型的官方契约测试确认。
- `RERANK_PROVIDER=none` 默认关闭。Alibaba `qwen3-rerank` 使用单独的 `RERANK_BASE_URL=https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/compatible-api/v1`，不得误用 Chat/Embedding 的 `compatible-mode/v1` endpoint。
- Rerank 故障或 cloud policy 拒绝会降级为原向量排序；confidential 未批准时 Rerank 和 LLM Provider 调用次数必须保持 0。
- 配置摘要只显示 Provider、model 和凭据是否 configured，不显示 Key、完整问题、片段或回答。

Chroma VectorStore 配置：

- Server 镜像固定为 `chromadb/chroma:1.5.9`，TypeScript 客户端固定为 `chromadb@3.5.0`。
- `CHROMA_TENANT`、`CHROMA_DATABASE` 必须与服务端资源一致。
- `CHROMA_COLLECTION_PREFIX` 只使用小写字母、数字、下划线和短横线。
- `CHROMA_SCHEMA_VERSION` 变化会创建新 collection，不覆盖旧 collection。
- `CHROMA_UPSERT_BATCH_SIZE` 控制单次写入，`CHROMA_QUERY_MAX_TOP_K` 限制检索规模。

查询 API 配置：

- `QUERY_RECALL_TOP_K=20` 控制 ACL 预过滤后的向量召回上限，且不得超过 `CHROMA_QUERY_MAX_TOP_K`； `RERANK_TOP_K=5` 同时作为最终上下文上限，不能大于召回数量。
- `QUERY_MAX_DISTANCE=0.45` 是 cosine distance 拒答阈值，数值越小越严格；上线前必须用阶段 14 评测集校准，不得为了提高回答率直接放宽。
- `QUERY_ANSWER_MODE=hybrid` 为默认混合模式：无足够知识库依据时只发送问题、不发送片段，返回明确标记的通用知识补充。设置为 `strict` 时保持无依据拒答；正式阶段 14 质量采集强制要求 `strict`，否则 CLI 拒绝运行。
- 混合模式不放宽出网规则：问题的 `defaultSensitivity` 为 confidential 或命中显式阻止规则时，通用 LLM 调用次数必须为 0。权限在生成期间变化时始终拒答。
- `QUERY_NEIGHBOR_WINDOW=1` 从 PostgreSQL 合并命中 chunk 前后各一个 active 相邻片段，所有相邻片段仍执行 tenant/ACL 与 active version 校验。
- `QUERY_MAX_MERGED_CONTEXT_CHARS=20000` 限制单个连续上下文，`QUERY_MAX_RERANK_INPUT_CHARS=120000` 限制一次 Rerank 的上下文字符总量；不得设为无上限。
- `QUERY_USER_RATE_LIMIT_PER_MINUTE=20` 和 `QUERY_TENANT_RATE_LIMIT_PER_MINUTE=200` 由 Redis 原子执行。Redis 故障时查询返回 503，不能继续调用 Embedding/Rerank/LLM。
- `QueryAudit` 不保存问题或回答正文，使用 `answerMode=grounded|general` 区分知识库与通用回答。若 LLM 已调用但最终因资料不足或无有效引用而拒答，仍记录实际 LLM Provider/model；仅有 Embedding Provider 表示流程在检索阶段结束。数据库迁移、备份、保留策略和只读审计访问必须覆盖该表。

从 1.0.20 升级到 1.5.9 时保留 `chroma_data` volume，由 Chroma 自身执行兼容升级。升级前生产环境必须备份 volume；禁止通过删除 volume 解决版本问题。升级后运行 heartbeat、version、collection 创建、stable upsert、tenant filter 和 delete 集成测试。

readiness 在启用 Embedding Provider 时会验证 active collection 指纹与 cosine 配置。不兼容时返回 `configuration_mismatch`，运维应创建新 collection 并重建，不得修改 metadata 伪造兼容。

入库可靠性配置：

- `INGESTION_MAX_ATTEMPTS` 控制 BullMQ 最大尝试次数。
- `INGESTION_RETRY_BASE_DELAY_MS` 控制指数退避基础延迟。
- Parser 超时、网络故障、429/5xx、Embedding retryable 错误和 Chroma unavailable 可以重试。
- Parser/Embedding 认证、参数错误、无效响应和索引配置不兼容不会盲目重试。
- 失败任务保留在 BullMQ failed 集合，并可通过 `GET /v1/ingestion-jobs/failed` 按 tenant 查询摘要。
- `local_prepared` checkpoint 表示解析、分块、脱敏和策略结果已落 PostgreSQL；重启或重试后直接继续 Embedding/索引，不重新创建策略事件。
- 未配置 Embedding 时，完成本地处理的文档显示为“待建立索引”（`prepared`）。配置完成后，在文档详情点击“继续建立索引”即可复用本地 chunk，跳过重新解析和上传。
- 配置摘要只输出 endpoint host 和凭据是否已配置，不输出连接串、密码、token 或 Key。
- 删除先进入 `deleting` 墓碑状态并停止相关 job，再删除 Chroma 向量和本地数据。若 Chroma 暂时失败，保持 deleting 并通过重复 DELETE 继续补偿；不得手工把状态改回 active。

## 7. 反向代理与 TLS

服务器对外只开放 80/443，API 绑定回环或 Docker 内网。反向代理需要：

- 自动 HTTPS。
- 上传大小限制与项目 `MAX_UPLOAD_MB` 一致。
- 请求超时：普通查询和文件上传分别配置。
- 基础 IP 限流；业务层继续按用户/tenant 限流。
- 转发 `X-Request-ID` 或生成 trace ID。
- 不缓存带认证的知识库回答。
- 安全响应头。
- 为前端提供 `apps/web/dist`，并将 Vue history 路由回退到 `index.html`。
- 仅将 `/v1` 和 `/health` 反向代理到回环或内部网络中的 NestJS API；不得代理其他内部服务。

Python Worker、Redis、PostgreSQL、Chroma 永远不经过公网反向代理。

## 8. 密钥管理

### 认证：OIDC/JWT 或账号密码会话

- production 必须设置 `AUTH_REQUIRED=true`。
- 默认模式是 OIDC/JWT：`PASSWORD_AUTH_ENABLED=false` 时必须配置下面的 OIDC 项。
- 如组织批准使用账号密码，设置 `PASSWORD_AUTH_ENABLED=true`，并由 Secret Manager、Vault、Docker Secret 或 Kubernetes Secret 注入 `PASSWORD_AUTH_USERS_JSON`。该 JSON 中每个账号包含 username、至少 12 位 password、tenantId、userId、department、`roles`（`["user"]` 或 `["admin"]`）、allowedSensitivities、capabilities 和 defaultSensitivity；禁止写入 `.env.example`、Compose、镜像、CI 输出或应用日志。
- 账号密码模式会签发 `HttpOnly; SameSite=Strict` Cookie，production 还会添加 `Secure`。必须先完成 HTTPS/TLS，并验证反向代理不会删除 `Set-Cookie`；会话默认 8 小时，可用 `PASSWORD_AUTH_SESSION_TTL_SECONDS` 在 5 分钟至 24 小时内调整。`PASSWORD_AUTH_MAX_ATTEMPTS` 与 `PASSWORD_AUTH_WINDOW_SECONDS` 控制单实例的登录失败限速。
- 启用账号密码模式时，OIDC 环境变量不参与 guard；如需恢复 OIDC，关闭 `PASSWORD_AUTH_ENABLED` 并配置 OIDC。
- OIDC 模式下，`OIDC_ISSUER` 和 `OIDC_AUDIENCE` 必须与访问 token 的签发配置完全一致。
- `OIDC_JWKS_URI` 在 production 必须使用 HTTPS，禁止 URL 内嵌用户名或密码。
- `OIDC_ALLOWED_ALGORITHMS_JSON` 只允许批准的 RSA/ECDSA 非对称算法，不允许 `none` 或 HMAC。
- `OIDC_CLOCK_TOLERANCE_SECONDS` 只用于有限时钟漂移，不应放大以掩盖服务器时间错误。
- `OIDC_JWKS_TIMEOUT_MS` 限制 JWKS 获取等待时间；密钥轮换依赖 JWKS kid，禁止把公钥写死在业务代码。
- token claims 必须包含 sub、tenantId、department、`roles`（`["user"]` 或 `["admin"]`）、allowedSensitivities、capabilities 和 defaultSensitivity。不要在反向代理中根据客户端 header 伪造这些 claims。
- tenant 级审计读取必须显式授予 `audit:read`，不能仅根据 `admin` 角色推导。
- Provider 与系统状态读取必须显式授予 `system:read`；`GET /v1/system/providers` 不返回 Key、完整 endpoint 或 collection 名称，`GET /v1/system/status` 不返回内部地址、路径和堆栈。两条接口的刷新都不执行付费 Provider 合成检查。
- 已验证用户目录必须显式授予 `access:read`。只有 `admin` 可读取当前 tenant 全范围，其他获授权身份固定为自身 department；不得通过代理或客户端 query 传入 tenant。目录由成功访问 `/v1/auth/session` 的已验证身份逐步建立，不是 OIDC 全量用户同步。
- 角色与部门 mutation 必须同时具备 `access:write` 和有效 `admin` 角色。应用托管角色在后端 guard 中解析，但不能增加 JWT capability；部门策略只与 JWT 敏感度取交集。上线 migration 后必须确认至少保留一个有效管理员，并将 `AccessAudit` 纳入审计保留与告警。角色只允许 `user` 或 `admin`；升级时仅旧 `platform_admin` 自动迁移为 `admin`，其他旧角色降为 `user`，避免扩大访问范围。

### 本地

- Key 存 `.env`。
- `.env` 必须加入 `.gitignore`。
- 使用额度受限的开发 Key。

### 服务器

- 使用云 Secret Manager、Vault、Docker Secret 或 Kubernetes Secret。
- 不把 Key 写进 Compose 文件、镜像层或 CI 日志。
- 开发、测试、生产使用不同 Key。
- 按 Provider 和用途拆分 Key。
- 设置预算、速率、IP/权限限制。
- 制定轮换和泄露撤销流程。

轮换顺序：新增 Key → 更新 Secret → 滚动重启 → 验证 → 撤销旧 Key。

## 9. 数据目录与权限

| 数据            | 位置              | 写入者       | 读取者                  |
| --------------- | ----------------- | ------------ | ----------------------- |
| 原始文件        | `raw_docs` volume | API          | API、Parser Worker 只读 |
| 元数据/ACL/任务 | PostgreSQL        | API/Consumer | API/Consumer            |
| 队列状态        | Redis             | API/Consumer | API/Consumer            |
| 向量            | Chroma volume     | API/Consumer | API                     |
| 临时解析文件    | Worker tmpfs      | Worker       | Worker                  |
| 日志            | stdout/采集系统   | 各服务       | 运维平台                |

上传目录禁止执行；Worker 使用只读挂载；临时文件放 tmpfs 并在任务结束清理。

### 9.1 CAD / DWG 转换流程

DXF 可直接上传，由 Parser Worker 使用固定版本 `ezdxf` 在本地解析。`MAX_CAD_ENTITIES` 控制单文件最多遍历的 CAD 实体数，`MAX_CAD_INSERT_DEPTH` 控制嵌套块引用深度；达到限制时任务失败或产生安全warning，不能通过调高到无上限规避异常图纸。默认 `MAX_CAD_ENTITIES=1000000`，配置 schema 的硬上限仍为 2,000,000；该默认值已覆盖遍历 774,303 个实体、输出 989 个元素的复杂 DWG 样本。调整前仍应在隔离环境记录实际遍历数、输出元素数和耗时。资源限制失败通过 `x-parser-error-code` 返回 allowlist 内的稳定安全错误码，主服务不得记录或透传 Worker 原始异常正文。

DWG 可直接上传。Consumer 先把任务状态写为 `converting`，Parser Worker 校验 DWG 签名后，在任务私有 tmpfs 目录调用 ODA File Converter 输出 DXF，再交给固定版本 `ezdxf` 解析。转换失败、超时、产物为空、超限或不安全时任务失败，不得继续分块或向量化；原始 DWG 不被覆盖，临时 DXF 在请求结束时删除。

ODA File Converter 是独立授权的第三方组件，仓库和基础 Worker 镜像不分发它。部署步骤：

1. 从 [ODA 官方下载页](https://www.opendesign.com/guestFiles/oda_file_converter) 获取与目标操作系统和 CPU 架构匹配的安装包，完成组织内部许可证审批、恶意代码扫描和校验和登记，并固定版本。本项目的 Mac 本地 DWG 流程使用官方 Linux x64 Debian 包，不使用 macOS 应用。
2. 将该包重命名为 `oda-file-converter.deb` 并放到 `apps/parser-worker/vendor/oda/`；该目录规则会忽略 `.deb`，不能提交安装包、许可证或凭据。使用 `docker compose -f compose.yaml -f compose.dwg.yaml up -d --build` 构建派生 Worker。该 override 固定 Worker 为 `linux/amd64`，Docker Desktop 会在 Apple Silicon 上兼容执行它。
3. 将 `DWG_CONVERTER_EXECUTABLE` 配置为镜像内真实、绝对、非符号链接的可执行文件路径。不得依赖 `PATH` 自动发现，也不得让上传请求指定路径或参数。
4. 确认 `PARSER_TEMP_PATH` 是仅 Worker 用户可写的 tmpfs，设置转换超时、最大 DXF 产物大小和输出版本，并保持默认的 `DWG_CONVERSION_ENABLED=true`。
5. 重启 Worker 并检查 `/health/ready` 中 `dwgConverter.status=up`，再用不含敏感数据的固定 DWG 样本执行冒烟测试，核对布局、图层、单位、TEXT/MTEXT、块属性、尺寸和外部参照 warning。

```dotenv
DWG_CONVERSION_ENABLED=true
DWG_CONVERTER_EXECUTABLE=/usr/local/bin/nexus-oda-file-converter
DWG_CONVERTER_RELEASE=<通过 dpkg-query -W odafileconverter 读取的实际版本>
DWG_OUTPUT_VERSION=ACAD2018
DWG_CONVERSION_TIMEOUT_SECONDS=180
PARSER_REQUEST_TIMEOUT_MS=240000
PARSER_TEMP_PATH=/tmp/parser
MAX_DWG_CONVERTED_BYTES=209715200
```

`DWG_CONVERTER_RELEASE` 是写入 parser version 的审计标签，必须与实际安装版本一致。本项目的本地 DWG 派生镜像提供了固定的、非符号链接的启动器 `/usr/local/bin/nexus-oda-file-converter`：它只转交 Worker 生成的固定参数，并在隔离虚拟显示中运行 ODA。整个 `/tmp` 使用受限 tmpfs，以让虚拟显示创建 Unix socket；入口脚本随后以 Worker 身份创建权限为 `1700` 的 `PARSER_TEMP_PATH`，根文件系统仍保持只读。构建后使用 `dpkg-query -W odafileconverter` 读取实际版本，将该版本填入 `DWG_CONVERTER_RELEASE`。Worker readiness 在默认启用转换时强制检查可执行文件和临时目录；未安装转换器时，默认启动必须失败关闭。只有组织明确选择不处理 DWG 时，才可显式设置 `DWG_CONVERSION_ENABLED=false` 并使用基础 Worker 镜像；此时 API 会拒绝 DWG 上传并返回稳定错误码 `DWG_CONVERSION_DISABLED`。

## 11. Embedding 索引迁移

以下任一变化都需要新索引：

- Provider。
- 模型或重要模型版本。
- 向量维度。
- document/query 任务规则。
- 关键分块或脱敏规则。

安全迁移：

1. 创建带新配置指纹的 collection。
2. 从 active 文档版本重新分块/Embedding。
3. 保存重建 checkpoint。
4. 使用评测集验证新索引。
5. 短时间灰度或影子查询。
6. 原子切换 active collection 配置。
7. 保留旧 collection 回滚。
8. 过期后删除旧索引。

严禁直接把新向量写入旧 collection。

当前实现使用 API 应用的独立 CLI 进程执行离线重建。先保持旧 API 和旧配置正常服务，在准备进程中加载目标 Embedding 配置并执行：

```bash
INDEX_MIGRATION_ACTION=prepare pnpm --filter @nexus-kb/api index:migrate
```

该模式不会启动普通 ingestion consumer，也不会修改任何文档的 `activeVersion`。每个候选版本完成稳定 ID upsert 和回读确认后保存为 `prepared`；任一文档失败时命令失败，旧索引继续生效。准备完成后必须先运行阶段 14 评测、确认 confidential 策略、备份 PostgreSQL/Chroma，并核对输出的 fingerprint 和 collection。

切换时进入受控发布窗口，先停止会改变文档版本的 mutation，使用同一目标配置执行：

```bash
INDEX_MIGRATION_ACTION=activate pnpm --filter @nexus-kb/api index:migrate
```

命令确认每个 active 文档都有匹配目标指纹的候选，并在一个 PostgreSQL transaction 中原子切换；缺候选或并发版本变化会整体回滚。随后立即把查询 API 发布到同一 Embedding 配置。旧版本与旧 collection 默认保留。需要回滚时恢复旧 Embedding 配置，再执行 `activate` 激活匹配旧指纹的 `superseded` 版本，并回切 API 配置。由于查询向量空间由进程配置决定，数据库切换与 API 配置发布必须协调在同一维护窗口，不能只执行其中一步。

## 12. 备份与恢复

### 12.1 需要备份

- PostgreSQL。
- Chroma 持久化 volume。
- 原始文档或对象存储。
- 生产配置的非敏感部分。
- 审计日志。

Redis 队列是否备份取决于业务恢复目标；持久化任务事实应以 PostgreSQL 为准，不只依赖 Redis。

### 12.2 一致性

原始文档、PostgreSQL 和向量索引之间存在引用关系。推荐：

- PostgreSQL 和原始文档为事实源。
- Chroma 可由 active 文档重新构建。
- 备份记录 Embedding 配置指纹。
- 恢复后运行引用完整性检查。

### 12.3 恢复演练

至少每季度验证：

- 在隔离环境恢复 PostgreSQL。
- 恢复或重建 Chroma。
- 随机抽取文档验证上传、检索和引用。
- 确认权限仍正确。
- 记录实际 RPO/RTO。

没有实际恢复演练的备份不能视为可用备份。

## 13. 监控与告警

### 13.1 API

- 请求量、4xx/5xx。
- P50/P95/P99。
- 活跃 tenant/用户。
- 限流次数。

### 13.2 模型 Provider

- 调用次数、429、5xx、超时。
- P95 延迟。
- 重试和备用 Provider 使用次数。
- 输入/输出 token 或字符数。
- 每日/每 tenant 成本。

### 13.3 入库

- 队列长度和最老任务等待时间。
- 每阶段耗时。
- 解析失败率。
- Embedding 失败块数。
- dead-letter 数量。

### 13.4 基础设施

- CPU、内存、磁盘、inode。
- PostgreSQL 连接和慢查询。
- Redis 内存和 rejected connection。
- Chroma 查询延迟、数据量和健康状态。
- Worker OOM/重启。

### 13.5 建议告警

- API 5xx 持续超阈值。
- Provider 429/5xx 激增。
- 队列持续积压。
- dead-letter 大于 0。
- 磁盘使用超过 75%/85%。
- 备份失败。
- confidential 出网拦截异常增加。
- collection 指纹不一致导致 ready 失败。

### 13.6 `/metrics` 指标与抓取边界

`/metrics` 使用 Prometheus text exposition，应用层不要求业务 JWT，以便监控系统抓取；反向代理或网络策略必须只允许监控网段访问，不得暴露到公网。指标 label 只允许稳定路由模板、状态类别、Provider、model、错误类别、队列状态和依赖名称，禁止 userId、tenantId、documentId、jobId、traceId、原始 URL 或正文。

核心指标：

- `nexuskb_http_request_duration_seconds`、`nexuskb_http_requests_total`：HTTP 分位数与错误率。
- `nexuskb_provider_request_duration_seconds`、`nexuskb_provider_requests_total`、 `nexuskb_provider_retries_total`：Provider 延迟、429、timeout、unavailable（5xx/网络不可用）和重试。
- `nexuskb_provider_tokens_total`、`nexuskb_provider_estimated_cost_usd_total`：模型用量和显式价格估算成本。
- `nexuskb_ingestion_queue_jobs`、`nexuskb_ingestion_queue_oldest_wait_seconds`、 `nexuskb_ingestion_job_duration_seconds`：队列积压、等待与任务耗时。
- `nexuskb_parser_requests_total`、`nexuskb_parser_request_duration_seconds`、 `nexuskb_parser_ocr_warnings_total`：解析失败、耗时与 OCR warning。
- `nexuskb_retrieval_results_total`、`nexuskb_rerank_degradations_total`：空检索与 Rerank 降级。
- `nexuskb_disk_usage_ratio`、`nexuskb_dependency_up{component="chroma"}`：磁盘和 Chroma 健康。

价格表按每百万 token 的 USD 输入/输出价配置。价格会变化，更新前必须核对供应商官方账单页面；未配置条目不会产生估算成本，但 token 计数仍保留。示例只展示结构，不代表真实价格：

```dotenv
MODEL_PRICING_USD_PER_MILLION_TOKENS_JSON={"provider:model":{"input":0,"output":0}}
```

推荐 PromQL（阈值应根据容量测试调整）：

```promql
# API 5xx 比例连续 10 分钟超过 5%
sum(rate(nexuskb_http_requests_total{status_class="5xx"}[10m]))
/
clamp_min(sum(rate(nexuskb_http_requests_total[10m])), 0.001) > 0.05

# API P95 超过 2 秒
histogram_quantile(0.95, sum by (le) (rate(nexuskb_http_request_duration_seconds_bucket[10m]))) > 2

# Provider 429 或 unavailable 持续出现
sum(rate(nexuskb_provider_requests_total{error_kind="rate_limit"}[5m])) > 0.1
sum(rate(nexuskb_provider_requests_total{error_kind="unavailable"}[5m])) > 0.1

# 队列积压、等待过久或存在失败任务
nexuskb_ingestion_queue_jobs{state="waiting"} > 100
nexuskb_ingestion_queue_oldest_wait_seconds > 300
nexuskb_ingestion_queue_jobs{state="failed"} > 0

# 解析失败率超过 5%
sum(rate(nexuskb_parser_requests_total{status="error"}[15m]))
/
clamp_min(sum(rate(nexuskb_parser_requests_total[15m])), 0.001) > 0.05

# 检索空结果率超过 30%
sum(rate(nexuskb_retrieval_results_total{outcome="empty"}[15m]))
/
clamp_min(sum(rate(nexuskb_retrieval_results_total[15m])), 0.001) > 0.30

# 磁盘 warning/critical 与 Chroma 不健康
nexuskb_disk_usage_ratio{path="raw_docs"} > 0.75
nexuskb_disk_usage_ratio{path="raw_docs"} > 0.85
nexuskb_dependency_up{component="chroma"} == 0
```

## 14. 日志与审计

日志应包含：timestamp、level、service、traceId、tenantId、userId、jobId、documentId、provider、model、durationMs、status。

日志不得包含：

- API Key、Authorization header、Cookie。
- 完整问题、原文片段和完整回答。
- 未脱敏个人信息。
- Worker 的宿主机绝对路径。
- 供应商返回的敏感原始响应。

CloudPolicyEvent 是可审计策略记录，但不保存原文、脱敏文本或匹配到的 PII。排障时只能通过 tenant/document/job/version、reasonCode、策略版本和 trace 关联定位，不得为了方便把正文补进日志。

审计事件与调试日志分开设置保留周期。审计记录发送过哪些 chunk ID，而不是默认保存 chunk 全文。

`GET /v1/audit/events` 合并查询 QueryAudit、DocumentLifecycleAudit 和 CloudPolicyEvent，最多返回 100 条，支持 `type`、`before` 和 `limit`。接口必须携带受验证身份和 `audit:read`，每类查询都固定当前 tenantId；返回内容不包含问题、回答、文档片段、解析元素、原文或脱敏正文。分页 `nextBefore` 是时间游标，不应被当作权限凭据。

## 15. 扩缩容

### 15.1 API

API 保持无状态，可水平扩容。session 使用签名 token 或外部存储，不保存在单进程内存。

### 15.2 Consumer 与 Parser Worker

- BullMQ consumer 可增加实例。
- Parser Worker 按 CPU/内存扩容。
- 限制每个 Worker 并发，避免 OCR 模型多份加载。
- 对超大文件使用独立队列。

### 15.3 Chroma 边界

出现以下情况考虑 Qdrant/Milvus：

- 多实例高并发写。
- 单机容量或延迟达不到目标。
- 需要成熟高可用、分片和备份。
- 过滤和运营能力不足。

迁移通过 VectorStore 接口完成，不修改业务 API。

## 17. 常见故障处理

### 上传成功但任务一直 queued

检查 Redis、BullMQ consumer、队列名称、consumer 日志和 dead-letter。确认 jobId 未因去重策略被错误复用。

### 重复上传返回 DOCUMENT_DUPLICATE

系统按 tenant、内容哈希、department、sensitivity 和 owner 判断 ACL 等价重复。确认是否应复用已有文档；如果原文档已经软删除，可重新上传。不要通过删除唯一索引绕过去重。

### 任务失败但 retryable=true

检查 `checkpoint` 和 `errorCategory`。`checkpoint=local_prepared` 时原始解析结果已经安全保存，恢复任务会从 Embedding/Chroma 继续。达到最大尝试次数后任务保留在 failed 集合，需排除上游故障后再提供人工重试入口。

### 任务停在 parsing

检查 Worker 健康、共享 volume、内部 token、解析超时和内存。大 PDF/OCR 可能触发 OOM，应降低并发或单独队列。

### Embedding 返回维度错误

立即停止写入。核对 model、dimensions、Provider 参数和 collection 指纹。不要截断或补零伪造兼容。

### 切换模型后检索质量突然变差

检查是否错误复用了旧 collection，文档与查询是否使用同一模型，以及 Google 等 Provider 的 document/query 任务规则是否正确。

### 用户查到其他部门内容

视为安全事件：暂停查询入口，保留审计证据，检查 tenant/ACL filter 和缓存键，确认 Rerank/相邻块合并没有绕过二次授权。

### Provider 大量 429

降低并发和批量、启用指数退避、检查账户配额。LLM 可切已批准的备用 Provider；Embedding 不得直接切换后继续查询旧索引。

### Chroma 数据损坏或丢失

停止写入，恢复备份；若无法可靠恢复，以 PostgreSQL active 文档和原始文件为事实源重建索引。
