# 知识库部署运维手册

> 适用架构：TypeScript/NestJS 主服务 + Python/FastAPI 解析 Worker
> 部署路径：Mac Docker Compose 验证 → Linux 单机 Compose → 按容量拆分服务

公开 API 的认证、capability/ACL、端点目录、错误码和安全调用示例见 [07-API使用说明.md](./07-API使用说明.md)；本文只负责部署、配置、监控和运维边界。

## 1. 部署拓扑

### 1.1 Mac 本地

```text
localhost
├── Vue Web:5173                   Vite 开发服务器；仅宿主机开发时启动
├── API:3000                       唯一默认映射的 Compose 服务
└── PostgreSQL:15432               仅加载 compose.db-gui.yaml 时绑定 127.0.0.1

Docker Compose
├── edge 网络
│   └── api:3000                    同时连接 backend；映射为 127.0.0.1:3000
└── backend 内部网络
    ├── parser-worker:8000          常规文件解析；不映射宿主机端口
    ├── tika:9998                   PDF 受控兜底；不映射宿主机端口
    ├── reranker-worker:8100        本地 BGE Rerank Worker；不映射宿主机端口
    ├── postgres:5432               元数据与任务状态；不映射宿主机端口
    ├── redis:6379                  BullMQ 任务队列；不映射宿主机端口
    ├── chroma:8000                 向量库；不映射宿主机端口
    └── deployment-agent:8200       仅 `configuration` profile 启用；受控配置发布

按需叠加
├── compose.dwg.yaml
│   └── parser-worker-dwg:8000      固定 linux/amd64；仅处理 .dwg，复用 backend 内网
└── compose.db-gui.yaml
    └── postgres:5432 → 127.0.0.1:15432
```

为避免反复书写 Compose 文件组合，统一从仓库根目录使用以下入口：`pnpm docker:dev -- <子命令>`（推荐本地开发，含 deployment-agent）、`pnpm docker:base -- <子命令>`（基础自检）、`pnpm docker:full -- <子命令>`（DWG + deployment-agent）或 `pnpm docker:full:db -- <子命令>`（完整服务 + DBeaver）。这里的 `full` 只表示 Compose 服务拓扑，不是产品版本。`docker:dev` 启用 `configuration` profile；`docker:full` 额外加载 `compose.dwg.yaml`；`docker:full:db` 再额外加载 `compose.db-gui.yaml`。全部常驻 Docker 服务可通过 `pnpm docker:up:all` 启动，但必须先完成 ODA 包配置。

基础自检模式只启动基础 Compose 服务；推荐本地开发与完整模式均启动 `deployment-agent`。完整模式同时运行原生 `parser-worker` 和 `parser-worker-dwg`，API 仅将 `.dwg` 请求路由到后者。DBeaver 入口仅绑定 PostgreSQL 至 `127.0.0.1:15432`；生产环境不得使用。除 API 外，其他 Compose 服务均不映射宿主机或公网端口。

`deployment-agent` 是唯一挂载 `/var/run/docker.sock` 的组件。它不接受公网流量、任意 shell、任意 Compose 文件、路径或服务名，只接受 API 使用内部 token 提交的固定配置 envelope，并只能重建 `api`、`parser-worker`、`parser-worker-dwg`、`reranker-worker`。API、Vue 和 Parser Worker 均不得挂载 Docker socket。

### 1.2 Linux 单机服务器

> [!IMPORTANT]
> 本节是阶段 16 的目标拓扑，尚不代表生产上线验收已通过。当前状态见 [TASK.md](../TASK.md)；在第 18–19 节的迁移、备份恢复、权限、压测和合规项全部验证前，不得将开发 Compose 配置直接视为生产部署方案。

```text
Internet
   │ HTTPS
   ▼
Nginx/Caddy
   │
   ▼
NestJS API ── Redis ── Ingestion Consumer
   │                        │
   │                        ▼
   │                   Python Parser Worker
   ├── PostgreSQL
   ├── Chroma
   └── Cloud Model APIs
```

所有内部服务位于私有 Docker network。Python Worker、Redis、PostgreSQL 和 Chroma 不直接暴露公网。

## 2. 环境要求

### 2.1 Mac 开发机

- Apple Silicon M1 Pro，16GB RAM。
- Docker Desktop 或兼容容器运行时。
- Node.js LTS、pnpm。
- Python 3.11（仅本地直接调试 Worker 时需要）。
- 建议预留 30GB 以上磁盘。

### 2.2 初期服务器

LLM 与可选 Rerank 使用云端 API；Embedding 也可使用本机 Ollama，因此起步不需要 GPU，但本机 Embedding 会占用开发机 CPU/内存：

- Linux x86_64 或 ARM64。
- 4 vCPU。
- 8–16GB RAM。
- 100GB 以上 SSD，按原始文档和向量规模调整。
- 固定出网、TLS 域名、备份存储。

OCR、LibreOffice 和大 PDF 解析会产生瞬时 CPU/内存压力：Parser Worker 从并发 1 开始，压测后再增加。镜像在构建期预置 OCR、语言模型和 CJK 字体，运行时不得下载；缓存仅可写入 Worker tmpfs。

DWG 模式额外启动仅处理 `.dwg` 的 `linux/amd64` Worker，常规 Worker 保持原生架构。两个 Worker 仅连接内部网络、只读挂载原始文件并复用内部 token；Tika 同样仅在内部网络可用。启动后以 Worker `/health/ready` 检查 `tika` 与 `dwgConverter` 状态。

## 3. 镜像设计

以仓库中的 Dockerfile 和 Compose 文件为唯一可执行定义，本手册不维护可复制的第二份镜像配方。发布镜像必须满足：锁文件安装、精确基础镜像版本、非 root 运行、只读根文件系统（临时目录除外）、最小权限和健康检查。

Parser Worker 默认单进程运行；OCR 模型会占用显著内存，扩容前先做容量测试。

## 4. Docker Compose

使用仓库 `compose.yaml` 及其受控覆盖文件，不在本文复制 Compose 示例。运行时必须使用 README 规定的 `pnpm docker:*` 入口；它们负责组合 Compose 文件和加载 `.env`、`config/runtime.env`。

部署前检查：镜像使用精确 tag；除 API 与本地 DBeaver 调试端口外不映射宿主机端口；原始文件以只读方式挂载给 Worker；临时目录使用 tmpfs；所有服务配置健康检查和 `no-new-privileges`。

## 5. 本地启动

### 5.1 首次启动

首次本地开发按根目录 [README](../README.md#第一次启动推荐本地开发模式) 配置 `.env` 中的数据库、Parser、配置加密和部署代理四项随机值，然后启动推荐模式：

```bash
docker info
docker compose version
pnpm docker:up:dev
pnpm docker:dev -- ps
curl --fail-with-body http://127.0.0.1:3000/health/ready
```

`docker:dev` 启动 API、deployment-agent、常规 Parser、Tika、Reranker、PostgreSQL、Redis 与 Chroma；它不要求 ODA，也不自动启用模型。要使用向量检索或问答，继续按 README 配置 Ollama 与 LLM；要使用 DWG，再按第 9.1 节准备 ODA 并切换至 `pnpm docker:full -- <子命令>`。

本地需要同时保留 DBeaver 端口时，改用 `pnpm docker:full:db -- <子命令>`。生产环境不得使用该入口。

验证：

```bash
curl http://127.0.0.1:3000/health/live
curl http://127.0.0.1:3000/health/ready
```

查看日志：

```bash
pnpm docker:dev -- logs -f api
pnpm docker:dev -- logs -f parser-worker tika
```

停止但保留数据：

```bash
pnpm docker:dev -- down
```

`docker compose down -v` 会删除 volumes，不得作为普通停止命令使用。

### 5.2 本地调试

需要直接运行主服务时，可让 Redis、PostgreSQL、Chroma 和 Worker 继续在容器中运行，并将这些端口只映射到 `127.0.0.1`。本机 `.env.local` 使用 localhost 地址，容器 `.env` 使用 service name。

### 5.3 `.env` 配置重载

环境变量在容器创建时读取。Vue 前端不在 Compose 中：页面、样式和普通前端源码由 Vite 热更新；修改 `vite.config.ts` 或前端 `VITE_*` 环境变量时停止并重新运行 `pnpm --filter @nexus-kb/web dev`。以下命令针对完整模式；推荐本地开发改用 `pnpm docker:dev --`，且不操作 `parser-worker-dwg`。

仓库提供的 `pnpm docker:base|dev|full|full:db --` 入口会先加载 `.env`，再在文件存在时加载 deployment-agent 管理的 `config/runtime.env`，并将同一顺序用于 Compose 变量插值。不得绕过这些入口直接执行一套缺少 `runtime.env` 的自定义 Compose 文件组合，否则可能让容器运行值与管理页激活版本再次漂移。基础/开发模式固定关闭 DWG；完整模式才允许激活配置控制 DWG 上传与内部路由。

| 改动范围                                           | 是否 build | 生效命令                                                     |
| -------------------------------------------------- | ---------- | ------------------------------------------------------------ |
| API `.env`：LLM、Embedding、查询、认证、ACL、限流  | 否         | `pnpm docker:full -- up -d --force-recreate api`             |
| API 源码、Dockerfile、API 依赖或 Prisma migration  | 是         | `pnpm docker:full -- up -d --build --force-recreate api`     |
| Parser `.env`：资源限制、CAD/DWG、临时目录         | 否         | `pnpm docker:full -- up -d --force-recreate parser-worker parser-worker-dwg` |
| Parser 源码、Dockerfile、Python 依赖或 ODA 安装包  | 是         | `pnpm docker:full -- up -d --build --force-recreate parser-worker parser-worker-dwg` |
| Rerank `.env`：Provider、模型、batch、内部令牌     | 否         | `pnpm docker:full -- up -d --force-recreate api reranker-worker` |
| Reranker 源码、Dockerfile 或 Python 依赖           | 是         | `pnpm docker:full -- up -d --build --force-recreate reranker-worker` |
| 首次启用 `local_bge`，或更换本地 BGE 模型 revision | 否         | 先执行 `pnpm docker:full -- --profile model-init run --rm reranker-model-init` 下载模型，再执行 `pnpm docker:full -- up -d --force-recreate api reranker-worker`。 |
| `PARSER_INTERNAL_TOKEN`                            | 否         | `pnpm docker:full -- up -d --force-recreate api parser-worker parser-worker-dwg reranker-worker`；`RERANK_INTERNAL_TOKEN` 留空时 Reranker 也依赖该值。 |
| Compose 文件、网络、volume 或 service 定义         | 视改动而定 | 先执行 `pnpm docker:full -- config --quiet`，再定向 `up -d --force-recreate <service>`；Dockerfile 变化时加 `--build`。 |
| PostgreSQL 初始化账号、数据库和密码                | 特殊处理   | 已有 volume 时不能靠重建修改，按下述规则操作。               |

共享 API 契约变更必须同步 API 与 Vue：执行 `pnpm build`，重建 API，并让 Vite 热更新或重启 Vite。API Key、模型名、超时和限流等运行配置变化不要求 `build`。重建后必须检查 `ps`、`/health/ready` 和相关服务日志。

`POSTGRES_USER`、`POSTGRES_DB` 和 `POSTGRES_PASSWORD` 是官方 PostgreSQL 镜像的初始化变量，只在空 `postgres_data` volume 首次启动时创建角色和数据库。已有 volume 时，`--force-recreate postgres` 不会修改数据库内部密码或重命名数据库。密码轮换应在受控维护窗口内完成：

1. 备份并确认当前数据库可恢复。
2. 在 PostgreSQL 内执行角色密码变更，不把新密码写入 shell 历史或日志。
3. 同步更新 `.env` 的 `POSTGRES_PASSWORD` 与 `DATABASE_URL`。
4. 重建 API 并验证 ready。

不得用 `docker compose down -v` 作为配置重载方式。Embedding Provider、模型、维度、关键分块或脱敏配置变化还需要新 collection 和索引迁移；重建 API 只会让新进程读取配置，不会自动证明旧索引兼容。

### 5.4 使用 DBeaver 只读查看 PostgreSQL

仓库的 `compose.db-gui.yaml` 仅用于本地调试：它把 PostgreSQL 加入现有 `edge` 网络，并仅绑定 Mac 回环地址 `127.0.0.1:15432`。启动数据库调试端口：

```bash
pnpm docker:full:db -- up -d postgres
```

DBeaver 使用 PostgreSQL 驱动，连接参数为：

```text
Host:     127.0.0.1
Port:     15432
Database: POSTGRES_DB（默认 kb）
Username: POSTGRES_USER（默认 kb）
Password: POSTGRES_PASSWORD
```

连接后通过 `kb → public → 表` 查看 `Document`、`DocumentVersion`、`IngestionJob`、`KnowledgeChunk`、`QueryAudit`、`UserDirectoryEntry` 等元数据。向量属于 Chroma，不在 PostgreSQL 中。调试连接建议设为只读；不得用 GUI 绕过 API 的 tenant、ACL、状态机、审计和删除流程直接修改业务数据。DB Browser for SQLite 与 NoSQLBooster for MongoDB 不支持本项目的 PostgreSQL。

整套服务需要持续开放 DBeaver 端口时，后续 Compose 命令应继续加载同一覆盖文件。结束调试并移除端口映射：

```bash
pnpm docker:full -- up -d --force-recreate postgres
```

该命令保留 `postgres_data` volume，只移除宿主机映射。生产部署禁止加载 `compose.db-gui.yaml`，PostgreSQL 仍应只位于私有 Docker network。

### 5.5 启用前端配置发布

此功能默认失败关闭。首次仍由运维编辑 `.env`，生成独立加密密钥与内部令牌并重建 API 与 deployment-agent。

> [!WARNING]
> 密钥不得提交 Git、复制到工单或日志。丢失 `SYSTEM_CONFIG_ENCRYPTION_KEY` 会使历史配置版本无法解密，必须纳入 Secret Manager 备份和轮换计划；轮换应先解密并重新加密历史 active/回滚版本，不能直接替换。

```bash
openssl rand -base64 32  # SYSTEM_CONFIG_ENCRYPTION_KEY
openssl rand -hex 32     # DEPLOYMENT_AGENT_TOKEN
```

将输出通过本地受保护 `.env` 或 Secret Manager 注入，并设置：

```dotenv
SYSTEM_CONFIG_ENCRYPTION_KEY=<base64 编码的 32 字节密钥>
DEPLOYMENT_AGENT_URL=http://deployment-agent:8200
DEPLOYMENT_AGENT_TOKEN=<至少 32 字符的独立随机 token>
```

写入后，从仓库根目录重建代理与 API：

```bash
pnpm docker:dev -- config --quiet
pnpm docker:dev -- up -d --build --force-recreate deployment-agent api
pnpm docker:dev -- ps
curl --fail-with-body http://127.0.0.1:3000/health/ready
```

必须从仓库根目录执行上述 Compose 命令。仓库的宿主机绝对路径会以相同路径挂载到 deployment-agent；这是代理通过宿主机 Docker socket 重建含相对 bind mount 的服务时，保证路径解析正确的必要条件。

管理页允许 LLM、Rerank、问答与限流、上传入库和 Parser/Tika/CAD/DWG 受控运行参数进入版本化流程。Parser、Tika 或 CAD/DWG 参数变更会固定重建常规与 DWG Parser Worker。数据库、Redis、认证根配置、内部 token、Compose/镜像/volume/网络以及 Embedding Provider/模型/维度仍由运维流程管理。管理员保存后，API 创建加密配置版本并计算受影响服务；代理原子写入 Git 忽略且权限为 `0600` 的 `config/runtime.env`，执行固定的 Compose `up -d --force-recreate --no-deps`，连续两次通过对应 readiness 后回调成功。

若 readiness 超时，代理自动恢复上一份 runtime env、再次重建相同服务并验证；页面显示“已自动回滚”。成功发布可从发布记录发起人工回滚，人工回滚同样创建受控异步任务。不得手工编辑 `config/runtime.env`，也不得用 `down -v` 处理发布失败。若状态为 `failed` 且错误码为 `ROLLBACK_FAILED`，立即停止进一步发布，检查代理、目标服务日志和上一版本配置，并按备份恢复。

## 6. 健康检查

### `/health/live`

只确认进程事件循环正常，不调用外部付费模型。

### `/health/ready`

确认：

- 配置已通过校验。
- PostgreSQL 可连接。
- Redis 可连接。
- Chroma 可连接且 collection 指纹兼容。
- Python Worker 可连接。
- 必要目录可读写。

ready 不应每次实际调用云端模型，以免产生费用和触发限流。云端 Provider 使用独立、低频的合成监控。

配置项、默认值与校验范围以 [`.env.example`](../.env.example) 和 API schema 为准；本文只保留运行规则：

- `ALLOW_CONFIDENTIAL_TO_CLOUD=false` 是默认值；本机 Ollama 例外也必须经 schema 白名单约束。
- 修改 Embedding Provider、模型、维度、关键分块或脱敏规则时，必须创建新 collection 并重建，不能混写旧索引。
- `EMBEDDING_PROVIDER=none` 可用于基础自检；启用云端 Provider 前确认 Key、HTTPS endpoint、区域和审批，启用 Ollama 时只允许受控本机地址。
- DWG 默认关闭；启用后必须使用完整 Compose 入口，并在 Worker readiness 中确认 `dwgConverter=up`。

付费 Provider 冒烟测试默认关闭。只允许使用专用测试 Key、脱敏合成输入并显式设置 `RUN_PAID_PROVIDER_TESTS=true`；普通 CI 不得调用付费服务。

正式质量评测属于付费、受控数据出网操作。数据集、身份映射和运行结果必须获批、Git 忽略且权限不宽于 `0600`；普通 CI 不得运行。具体采集、聚合命令与决策门槛见 [`evaluation/README.md`](../evaluation/README.md)。只有 `unauthorizedLeakRate=0` 且 `costCoverage=1`，才可据质量增益考虑启用 Rerank。

LLM、Rerank 的可选值和字段以 [`.env.example`](../.env.example) 为准。启用非 `none` Provider 时必须配置获批的 HTTPS endpoint、model 和凭据；仅可对可重试故障启用 LLM 备用 Provider。Rerank 默认关闭，故障或策略拒绝降级到向量排序；`confidential` 未获批准时 LLM/Rerank 调用次数必须为 0。Reranker 的模型下载、内部网络与 revision 固定要求见 [`apps/reranker-worker/README.md`](../apps/reranker-worker/README.md)。

Chroma 版本、collection 命名和查询参数以配置 schema 为准。运维只需遵守：保留 `chroma_data`，升级前备份；`ready` 报 `configuration_mismatch` 时创建新 collection 并重建，不得改 metadata 伪造兼容。

查询参数必须保持有界：召回数不超过 Chroma 上限，Rerank/LLM 上下文不超过预算。`hybrid` 可返回明确标记的通用知识补充，正式评测强制 `strict`；无论模式，confidential 策略与权限变化都必须失败关闭。完整链路约束见 [技术设计第 6、7、11 节](./02-技术设计.md)。

入库可靠性配置：

- `INGESTION_MAX_ATTEMPTS` 控制 BullMQ 最大尝试次数。
- `INGESTION_RETRY_BASE_DELAY_MS` 控制指数退避基础延迟。
- Parser 超时、网络故障、429/5xx、Embedding retryable 错误和 Chroma unavailable 可以重试。
- Parser/Embedding 认证、参数错误、无效响应和索引配置不兼容不会盲目重试。
- 失败任务保留在 BullMQ failed 集合，并可通过 `GET /v1/ingestion-jobs/failed` 按 tenant 查询摘要。
- `local_prepared` checkpoint 表示解析、分块、脱敏和策略结果已落 PostgreSQL；重启或重试后直接继续 Embedding/索引，不重新创建策略事件。
- 未配置 Embedding 时，完成本地处理的文档显示为“待建立索引”（`prepared`）。配置完成后，在文档详情点击“继续建立索引”即可复用本地 chunk，跳过重新解析和上传。
- 配置摘要只输出 endpoint host 和凭据是否已配置，不输出连接串、密码、token 或 Key。
- 删除先进入 `deleting` 墓碑状态并停止相关 job，再删除 Chroma 向量和本地数据。若 Chroma 暂时失败，保持 deleting 并通过重复 DELETE 继续补偿；不得手工把状态改回 active。

## 7. 反向代理与 TLS

服务器对外只开放 80/443，API 绑定回环或 Docker 内网。反向代理需要：

- 自动 HTTPS。
- 上传大小限制与项目 `MAX_UPLOAD_BYTES` 一致（该值以字节为单位）。
- 请求超时：普通查询和文件上传分别配置。
- 基础 IP 限流；业务层继续按用户/tenant 限流。
- 转发 `X-Request-ID` 或生成 trace ID。
- 不缓存带认证的知识库回答。
- 安全响应头。文档 PDF/Office 预览使用同源 `iframe`，因此入口代理必须使用 `X-Frame-Options: SAMEORIGIN` 和 `Content-Security-Policy: frame-ancestors 'self'`；不得全局设置 `X-Frame-Options: DENY`，也不得允许跨域嵌入。对上游 API 已返回的 CSP 必须追加而不是覆盖，以保留 SVG 预览的独立沙箱策略。
- 为前端提供 `apps/web/dist`，并将 Vue history 路由回退到 `index.html`。
- 仅将 `/v1` 和 `/health` 反向代理到回环或内部网络中的 NestJS API；不得代理其他内部服务。

Python Worker、Redis、PostgreSQL、Chroma 永远不经过公网反向代理。

## 8. 密钥管理

### 认证：OIDC/JWT 或账号密码会话

- production 必须设置 `AUTH_REQUIRED=true`。
- 默认模式是 OIDC/JWT：`PASSWORD_AUTH_ENABLED=false` 时必须配置下面的 OIDC 项。
- 如组织批准使用账号密码，设置 `PASSWORD_AUTH_ENABLED=true`，并由 Secret Manager、Vault、Docker Secret 或 Kubernetes Secret 注入 `PASSWORD_AUTH_USERS_JSON`。该 JSON 只在数据库尚未完成首次引导时导入至少一个管理员账号；之后新增、编辑、禁用、删除和密码重置均在后台完成，重启不会覆盖。每个引导账号包含 username、至少 12 位 password、tenantId、userId、department、`roles`（`["user"]` 或 `["admin"]`）、allowedSensitivities、capabilities 和 defaultSensitivity；禁止写入 `.env.example`、Compose、镜像、CI 输出或应用日志。
- 账号密码模式会签发 `HttpOnly; SameSite=Strict` Cookie，production 还会添加 `Secure`。必须先完成 HTTPS/TLS，并验证反向代理不会删除 `Set-Cookie`；会话默认 8 小时，可用 `PASSWORD_AUTH_SESSION_TTL_SECONDS` 在 5 分钟至 24 小时内调整。`PASSWORD_AUTH_MAX_ATTEMPTS` 与 `PASSWORD_AUTH_WINDOW_SECONDS` 控制单实例的登录失败限速。
- 启用账号密码模式时，OIDC 环境变量不参与 guard；如需恢复 OIDC，关闭 `PASSWORD_AUTH_ENABLED` 并配置 OIDC。
- OIDC 模式下，`OIDC_ISSUER` 和 `OIDC_AUDIENCE` 必须与访问 token 的签发配置完全一致。
- `OIDC_JWKS_URI` 在 production 必须使用 HTTPS，禁止 URL 内嵌用户名或密码。
- `OIDC_ALLOWED_ALGORITHMS_JSON` 只允许批准的 RSA/ECDSA 非对称算法，不允许 `none` 或 HMAC。
- `OIDC_CLOCK_TOLERANCE_SECONDS` 只用于有限时钟漂移，不应放大以掩盖服务器时间错误。
- `OIDC_JWKS_TIMEOUT_MS` 限制 JWKS 获取等待时间；密钥轮换依赖 JWKS kid，禁止把公钥写死在业务代码。
- token claims 必须包含 sub、tenantId、department、`roles`（`["user"]` 或 `["admin"]`）、allowedSensitivities、capabilities 和 defaultSensitivity。不要在反向代理中根据客户端 header 伪造这些 claims。
- `admin` 自动拥有审计、Provider、系统状态、账号和部门管理等全部应用 capability；Provider 与系统状态接口仍不返回 Key、完整 endpoint、collection、内部地址或堆栈，也不执行付费 Provider 合成检查。
- `admin` 可读取当前 tenant 全范围的用户目录，并创建、编辑、禁用、删除本地后台账号；外部 OIDC 身份账号仅由身份源管理。普通用户即使拥有 `access:read` 仍固定到自身 department；不得通过代理或客户端 query 传入 tenant。
- 角色与部门 mutation 需要有效 `admin` 角色。管理员在 guard 中自动获得完整 capability 和敏感度范围，但不能跨 tenant 或突破 confidential 出网策略。上线 migration 后必须确认至少保留一个有效管理员，并将 `AccessAudit` 纳入审计保留与告警。角色只允许 `user` 或 `admin`；升级时仅旧 `platform_admin` 自动迁移为 `admin`，其他旧角色降为 `user`。

### 本地

- Key 存 `.env`。
- `.env` 必须加入 `.gitignore`。
- 使用额度受限的开发 Key。

### 服务器

- 使用云 Secret Manager、Vault、Docker Secret 或 Kubernetes Secret。
- 不把 Key 写进 Compose 文件、镜像层或 CI 日志。
- 开发、测试、生产使用不同 Key。
- 按 Provider 和用途拆分 Key。
- 设置预算、速率、IP/权限限制。
- 制定轮换和泄露撤销流程。

轮换顺序：新增 Key → 更新 Secret → 滚动重启 → 验证 → 撤销旧 Key。

## 9. 数据目录与权限

| 数据            | 位置              | 写入者       | 读取者                  |
| --------------- | ----------------- | ------------ | ----------------------- |
| 原始文件        | `raw_docs` volume | API          | API、Parser Worker 只读 |
| 预览产物        | `preview_artifacts` volume | Parser Worker | API（读取/删除） |
| 元数据/ACL/任务 | PostgreSQL        | API/Consumer | API/Consumer            |
| 队列状态        | Redis             | API/Consumer | API/Consumer            |
| 向量            | Chroma volume     | API/Consumer | API                     |
| 临时解析文件    | Worker tmpfs      | Worker       | Worker                  |
| 日志            | stdout/采集系统   | 各服务       | 运维平台                |

上传目录禁止执行；Worker 使用只读挂载；临时文件放 tmpfs 并在任务结束清理。

`preview_artifacts` 由 Parser Worker 写入、API 在 ACL 通过后读取并在删除文档时清理；不得改为公共可写或手工修改业务产物。预览异常先检查 Worker warning、`previewArtifacts` / `officePreview` readiness、CJK 字体和 volume 权限；已有产物需通过正常重新索引或重新上传生成，不得删除 volume 规避。

### 9.1 CAD / DWG 转换流程

DXF 由本地 `ezdxf` 解析；实体数、嵌套深度、内存和超时始终受 schema 上限保护，不能以调大限制绕过异常图纸。资源限制只返回 allowlist 安全错误码。

CAD 预览按受控阈值在 SVG 与按需瓦片之间选择。瓦片 bundle 仅含服务端生成的非可执行索引和 PNG 缓存；运维人员不得直接修改 `preview_artifacts`。调整 `CAD_*` 配置后重建两个 Parser Worker；先用脱敏大图压测，再观察瓦片 p95、缓存命中、Worker 资源错误和磁盘使用后逐步放量。阈值、缓存和预算字段以 [`.env.example`](../.env.example) 为准，渲染机制见 [Parser Worker README](../apps/parser-worker/README.md)。

DWG 可直接上传。Consumer 先把任务状态写为 `converting`，Parser Worker 校验 DWG 签名后，在任务私有 tmpfs 目录调用 ODA File Converter 输出 DXF，再交给固定版本 `ezdxf` 解析。转换失败、超时、产物为空、超限或不安全时任务失败，不得继续分块或向量化；原始 DWG 不被覆盖，临时 DXF 在请求结束时删除。

ODA File Converter 是独立授权的第三方组件，仓库和基础 Worker 镜像不分发它。部署步骤：

1. 从 [ODA 官方下载页](https://www.opendesign.com/guestfiles/oda_file_converter) 获取与目标操作系统和 CPU 架构匹配的安装包，完成组织内部许可证审批、恶意代码扫描和校验和登记，并固定版本。本项目的 Mac 本地 DWG 流程使用官方 Linux x64 Debian 包，不使用 macOS 应用。
2. 将该包重命名为 `oda-file-converter.deb` 并放到 `apps/parser-worker/vendor/oda/`；该目录规则会忽略 `.deb`，不能提交安装包、许可证或凭据。

> [!IMPORTANT]
> **DWG 模式固定入口：** 从下一步开始，所有 Compose 命令使用 `pnpm docker:full -- <子命令>`。不得为了简写改回 `docker:dev`；推荐入口不包含 ODA Worker。修改 Parser/DWG 配置使用 `pnpm docker:full -- up -d --force-recreate parser-worker parser-worker-dwg api`；修改源码、Dockerfile 或 ODA 包使用 `pnpm docker:full -- up -d --build --force-recreate api parser-worker parser-worker-dwg reranker-worker`。

3. 使用 `pnpm docker:full -- up -d --build` 构建派生 Worker。完整入口固定 DWG Worker 为 `linux/amd64`，Docker Desktop 会在 Apple Silicon 上兼容执行它。
4. 将 `DWG_CONVERTER_EXECUTABLE` 配置为镜像内真实、绝对、非符号链接的可执行文件路径。不得依赖 `PATH` 自动发现，也不得让上传请求指定路径或参数。
5. 确认 `PARSER_TEMP_PATH` 是仅 Worker 用户可写的 tmpfs，设置转换超时、最大 DXF 产物大小和输出版本；完整入口会启用 DWG 路由，基础模式保持 `DWG_CONVERSION_ENABLED=false`。
6. 重启 Worker 并检查 `/health/ready` 中 `dwgConverter.status=up`，再用不含敏感数据的固定 DWG 样本执行冒烟测试，核对布局、图层、单位、TEXT/MTEXT、块属性、尺寸和外部参照 warning。

```dotenv
DWG_CONVERSION_ENABLED=true
DWG_CONVERTER_EXECUTABLE=/usr/local/bin/nexus-oda-file-converter
DWG_CONVERTER_RELEASE=<通过 dpkg-query -W odafileconverter 读取的实际版本>
DWG_OUTPUT_VERSION=ACAD2018
DWG_CONVERSION_TIMEOUT_SECONDS=180
PARSER_REQUEST_TIMEOUT_MS=240000
PARSER_TEMP_PATH=/tmp/parser
MAX_DWG_CONVERTED_BYTES=209715200
```

`DWG_CONVERTER_RELEASE` 必须与 `dpkg-query -W odafileconverter` 的实际版本一致。转换器只能使用镜像内固定、非符号链接的启动器和 Worker 私有 tmpfs；未通过 readiness 时失败关闭。确实不处理 DWG 时才设置 `DWG_CONVERSION_ENABLED=false`，此时 API 返回 `DWG_CONVERSION_DISABLED`。

## 11. Embedding 索引迁移

以下任一变化都需要新索引：

- Provider。
- 模型或重要模型版本。
- 向量维度。
- document/query 任务规则。
- 关键分块或脱敏规则。

安全迁移：

1. 创建带新配置指纹的 collection。
2. 从 active 文档版本重新分块/Embedding。
3. 保存重建 checkpoint。
4. 使用评测集验证新索引。
5. 短时间灰度或影子查询。
6. 原子切换 active collection 配置。
7. 保留旧 collection 回滚。
8. 过期后删除旧索引。

严禁直接把新向量写入旧 collection。

当前实现使用 API 应用的独立 CLI 进程执行离线重建。先保持旧 API 和旧配置正常服务，在准备进程中加载目标 Embedding 配置并执行：

```bash
INDEX_MIGRATION_ACTION=prepare pnpm --filter @nexus-kb/api index:migrate
```

该模式不会启动普通 ingestion consumer，也不会修改任何文档的 `activeVersion`。每个候选版本完成稳定 ID upsert 和回读确认后保存为 `prepared`；任一文档失败时命令失败，旧索引继续生效。准备完成后必须先运行正式质量评测、确认 confidential 策略、备份 PostgreSQL/Chroma，并核对输出的 fingerprint 和 collection。

切换时进入受控发布窗口，先停止会改变文档版本的 mutation，使用同一目标配置执行：

```bash
INDEX_MIGRATION_ACTION=activate pnpm --filter @nexus-kb/api index:migrate
```

命令确认每个 active 文档都有匹配目标指纹的候选，并在一个 PostgreSQL transaction 中原子切换；缺候选或并发版本变化会整体回滚。随后立即把查询 API 发布到同一 Embedding 配置。旧版本与旧 collection 默认保留。需要回滚时恢复旧 Embedding 配置，再执行 `activate` 激活匹配旧指纹的 `superseded` 版本，并回切 API 配置。由于查询向量空间由进程配置决定，数据库切换与 API 配置发布必须协调在同一维护窗口，不能只执行其中一步。

## 12. 备份与恢复

### 12.1 需要备份

- PostgreSQL。
- Chroma 持久化 volume。
- 原始文档或对象存储。
- 生产配置的非敏感部分。
- Secret Manager/Vault 中的 `SYSTEM_CONFIG_ENCRYPTION_KEY` 及可恢复当前服务所必需的密钥版本；备份仍必须加密、限权且不得导出到代码库或普通工单。
- 审计日志。

Redis 队列是否备份取决于业务恢复目标；持久化任务事实应以 PostgreSQL 为准，不只依赖 Redis。

### 12.2 一致性

原始文档、PostgreSQL 和向量索引之间存在引用关系。推荐：

- PostgreSQL 和原始文档为事实源。
- Chroma 可由 active 文档重新构建。
- 备份记录 Embedding 配置指纹。
- 恢复后运行引用完整性检查。

### 12.3 恢复演练

至少每季度验证：

- 在隔离环境恢复 PostgreSQL。
- 恢复或重建 Chroma。
- 随机抽取文档验证上传、检索和引用。
- 确认权限仍正确。
- 记录实际 RPO/RTO。

没有实际恢复演练的备份不能视为可用备份。

## 13. 监控与告警

### 13.1 API

- 请求量、4xx/5xx。
- P50/P95/P99。
- 活跃 tenant/用户。
- 限流次数。

### 13.2 模型 Provider

- 调用次数、429、5xx、超时。
- P95 延迟。
- 重试和备用 Provider 使用次数。
- 输入/输出 token 或字符数。
- 每日/每 tenant 成本。

### 13.3 入库

- 队列长度和最老任务等待时间。
- 每阶段耗时。
- 解析失败率。
- Embedding 失败块数。
- dead-letter 数量。

### 13.4 基础设施

- CPU、内存、磁盘、inode。
- PostgreSQL 连接和慢查询。
- Redis 内存和 rejected connection。
- Chroma 查询延迟、数据量和健康状态。
- Worker OOM/重启。

### 13.5 建议告警

- API 5xx 持续超阈值。
- Provider 429/5xx 激增。
- 队列持续积压。
- dead-letter 大于 0。
- 磁盘使用超过 75%/85%。
- 备份失败。
- confidential 出网拦截异常增加。
- collection 指纹不一致导致 ready 失败。

### 13.6 `/metrics` 指标与抓取边界

`/metrics` 使用 Prometheus text exposition，应用层不要求业务 JWT，以便监控系统抓取；反向代理或网络策略必须只允许监控网段访问，不得暴露到公网。指标 label 只允许稳定路由模板、状态类别、Provider、model、错误类别、队列状态和依赖名称，禁止 userId、tenantId、documentId、jobId、traceId、原始 URL 或正文。

核心指标：

- `nexuskb_http_request_duration_seconds`、`nexuskb_http_requests_total`：HTTP 分位数与错误率。
- `nexuskb_provider_request_duration_seconds`、`nexuskb_provider_requests_total`、 `nexuskb_provider_retries_total`：Provider 延迟、429、timeout、unavailable（5xx/网络不可用）和重试。
- `nexuskb_provider_tokens_total`、`nexuskb_provider_estimated_cost_usd_total`：模型用量和显式价格估算成本。
- `nexuskb_ingestion_queue_jobs`、`nexuskb_ingestion_queue_oldest_wait_seconds`、 `nexuskb_ingestion_job_duration_seconds`：队列积压、等待与任务耗时。
- `nexuskb_parser_requests_total`、`nexuskb_parser_request_duration_seconds`、 `nexuskb_parser_ocr_warnings_total`：解析失败、耗时与 OCR warning。
- `nexuskb_retrieval_results_total`、`nexuskb_rerank_degradations_total`：空检索与 Rerank 降级。
- `nexuskb_disk_usage_ratio`、`nexuskb_dependency_up{component="chroma"}`：磁盘和 Chroma 健康。

价格表按每百万 token 的 USD 输入/输出价配置。价格会变化，更新前必须核对供应商官方账单页面；未配置条目不会产生估算成本，但 token 计数仍保留。示例只展示结构，不代表真实价格：

```dotenv
MODEL_PRICING_USD_PER_MILLION_TOKENS_JSON={"provider:model":{"input":0,"output":0}}
```

PromQL 仅在配置监控规则时需要；阈值必须根据容量测试调整。

## 14. 日志与审计

日志应包含：timestamp、level、service、traceId、tenantId、userId、jobId、documentId、provider、model、durationMs、status。

日志不得包含：

- API Key、Authorization header、Cookie。
- 完整问题、原文片段和完整回答。
- 未脱敏个人信息。
- Worker 的宿主机绝对路径。
- 供应商返回的敏感原始响应。

CloudPolicyEvent 是可审计策略记录，但不保存原文、脱敏文本或匹配到的 PII。排障时只能通过 tenant/document/job/version、reasonCode、策略版本和 trace 关联定位，不得为了方便把正文补进日志。

审计事件与调试日志分开设置保留周期。审计记录发送过哪些 chunk ID，而不是默认保存 chunk 全文。

`GET /v1/audit/events` 合并查询 QueryAudit、DocumentLifecycleAudit 和 CloudPolicyEvent，最多返回 100 条，支持 `type`、`before` 和 `limit`。接口必须携带受验证身份和 `audit:read`，每类查询都固定当前 tenantId；返回内容不包含问题、回答、文档片段、解析元素、原文或脱敏正文。分页 `nextBefore` 是时间游标，不应被当作权限凭据。

## 15. 扩缩容

### 15.1 API

API 保持无状态，可水平扩容。session 使用签名 token 或外部存储，不保存在单进程内存。

### 15.2 Consumer 与 Parser Worker

- BullMQ consumer 可增加实例。
- Parser Worker 按 CPU/内存扩容。
- 限制每个 Worker 并发，避免 OCR 模型多份加载。
- 对超大文件使用独立队列。

### 15.3 Chroma 边界

出现以下情况考虑 Qdrant/Milvus：

- 多实例高并发写。
- 单机容量或延迟达不到目标。
- 需要成熟高可用、分片和备份。
- 过滤和运营能力不足。

迁移通过 VectorStore 接口完成，不修改业务 API。

## 17. 常见故障处理

### 上传成功但任务一直 queued

检查 Redis、BullMQ consumer、队列名称、consumer 日志和 dead-letter。确认 jobId 未因去重策略被错误复用。

### 重复上传返回 DOCUMENT_DUPLICATE

系统按 tenant、内容哈希、department、sensitivity 和 owner 判断 ACL 等价重复。确认是否应复用已有文档；如果原文档已经软删除，可重新上传。不要通过删除唯一索引绕过去重。

### 任务失败但 retryable=true

检查 `checkpoint` 和 `errorCategory`。`checkpoint=local_prepared` 时原始解析结果已经安全保存，恢复任务会从 Embedding/Chroma 继续。达到最大尝试次数后任务保留在 failed 集合，需排除上游故障后再提供人工重试入口。

### 任务停在 parsing

检查 Worker 健康、原文件/预览共享 volume、LibreOffice、内部 token、解析超时和内存。大 PDF/OCR 可能触发 OOM，应降低并发或单独队列。仅有 `PREVIEW_GENERATION_FAILED` 时 RAG 入库仍可成功，Web 会降级显示解析文本。

### Office 或 CAD 预览中文显示为方块

分别在常规与 DWG Worker 中运行 `fc-list :lang=zh`，必须能列出 Noto CJK；再用脱敏合成 DOCX/XLSX 和 DXF 验证 PDF 嵌入字体与 SVG 字形路径。若镜像仍无字体，使用带 `--build` 的完整模式重建两个 Worker，不能只重建容器。已生成的旧预览不会自动改写，应通过正常重新索引或重新上传再生成。

### Embedding 返回维度错误

立即停止写入。核对 model、dimensions、Provider 参数和 collection 指纹。不要截断或补零伪造兼容。

### 切换模型后检索质量突然变差

检查是否错误复用了旧 collection，文档与查询是否使用同一模型，以及 Google 等 Provider 的 document/query 任务规则是否正确。

### 用户查到其他部门内容

视为安全事件：暂停查询入口，保留审计证据，检查 tenant/ACL filter 和缓存键，确认 Rerank/相邻块合并没有绕过二次授权。

### Provider 大量 429

降低并发和批量、启用指数退避、检查账户配额。LLM 可切已批准的备用 Provider；Embedding 不得直接切换后继续查询旧索引。

### Chroma 数据损坏或丢失

停止写入，恢复备份；若无法可靠恢复，以 PostgreSQL active 文档和原始文件为事实源重建索引。
