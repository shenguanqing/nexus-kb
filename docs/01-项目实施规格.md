# 企业级知识库项目实施规格

> 文档版本：v1.0  
> 项目阶段：先在 Mac 本地跑通，后迁移 Linux 服务器  
> 核心架构：TypeScript 主服务 + Python 文档解析 Worker  
> 模型策略：LLM、Embedding、可选 Rerank 暂时全部使用云端 API

---

## 2. 项目目标

建设一套企业级知识库系统，第一阶段在 MacBook Pro M1 / 16GB 环境中完成以下闭环：

```text
文档上传
  → 本地解析
  → 结构化分块
  → 脱敏与数据出网检查
  → 云端 Embedding
  → 本地向量库
  → 带权限过滤的检索
  → 可选云端 Rerank
  → 云端 LLM 生成答案
  → 返回引用来源
  → 审计记录
```

本地验证完成后，应能在不重写核心业务代码的前提下部署到 Linux 服务器。

## 3. 技术边界

### 3.0 Vue 前端负责

- 知识问答、来源查看、文档管理、上传进度和管理后台界面。
- 登录状态、路由权限提示和统一 API 交互。
- 加载、空数据、错误、无权限和响应式状态。
- 前端权限只改善体验，所有资源访问仍由 TypeScript 主服务强制鉴权。

### 3.1 TypeScript 主服务负责

- 对外 REST API。
- 用户身份、租户、部门、角色和文档权限。
- 文档上传、任务创建、状态查询和删除。
- 调度 Python 解析 Worker。
- 分块后的脱敏、云端调用策略判断。
- OpenAI、Google、DeepSeek、Alibaba 等模型 Provider。
- Embedding、向量入库、检索、Rerank 和 LLM 编排。
- 引用校验、审计、指标、限流和错误处理。

### 3.2 Python Worker 负责

- PDF、DOCX、PPTX、HTML 等文档解析。
- XLSX 表格解析。
- 图片 OCR。
- DXF 文本提取。
- Tika 兜底解析。
- 返回统一的结构化元素，不负责用户权限、模型调用或向量库写入。

### 3.3 外部云服务负责

- LLM：OpenAI、Google Gemini、DeepSeek、阿里云百炼或其他 OpenAI-compatible 平台。
- Embedding：OpenAI、Google Gemini、阿里云百炼。
- Rerank：第一阶段默认关闭；需要时接入阿里云或其他服务。

DeepSeek 在本项目中只作为 LLM Provider，不假设其提供 Embedding。LLM 和 Embedding 必须独立配置。

## 4. 数据安全边界

| 阶段 | 是否出网 | 可能发送的数据 |
|---|---:|---|
| 文件保存与解析 | 否 | 无 |
| 分块与本地脱敏 | 否 | 无 |
| Embedding | 是 | 脱敏后的文档分块、用户问题 |
| 向量存储与 ACL 检索 | 否 | 无 |
| Rerank（启用时） | 是 | 用户问题和候选片段 |
| LLM | 是 | 用户问题和通过权限检查的少量片段 |

必须满足：

1. API Key 不得写入代码、Git、镜像、前端或日志。
2. `confidential` 文档默认禁止发送任何云端模型。
3. 文档在 Embedding 前完成脱敏和出网策略判断。
4. 检索必须先做租户和 ACL 过滤，不能检索后才补救。
5. 发给 Rerank/LLM 前再次执行权限与敏感度检查。
6. 日志默认不保存完整问题、片段和回答。
7. 服务端身份必须来自经过验证的 JWT/session，不能信任请求体中的角色或部门。

## 5. 功能范围

### 5.1 第一阶段必须实现

- 上传 TXT、Markdown、PDF、DOCX、XLSX 和常见图片。
- 创建异步入库任务并查询状态。
- 解析文档并返回页码、标题路径、表格等结构信息。
- 按结构优先、token 兜底的方式分块。
- 对文档分块进行基础 DLP/脱敏。
- 通过云端 API 生成文档和查询向量。
- 将文本、向量、来源和权限 metadata 存入 Chroma。
- 带租户、部门、敏感度条件的向量检索。
- 调用可配置的云端 LLM 回答。
- 回答必须包含文档、页码和 chunk 来源。
- 无充分依据时拒答。
- 支持删除文档及其全部向量。
- 记录结构化审计日志和 trace ID。
- 提供健康检查和基础指标。

### 5.2 第二阶段增强

- PPTX、HTML、EML、RTF、DXF。
- 云端 Rerank。
- 文档版本管理和无中断重建索引。
- PostgreSQL 保存用户、ACL、文档和任务状态。
- 企业 SSO/OIDC。
- 批量上传、断点续跑和 Embedding 缓存。
- 检索评测集、成本统计和质量看板。

### 5.3 暂不实现

- 本地大模型推理。
- 本地 Embedding 和本地 Rerank。
- 自动执行知识库文档中的操作指令。
- 复杂 Agent 工具链。
- 一开始就部署 Milvus/Kubernetes 等重型集群。

## 6. 支持的文档类型

| 类型 | 第一阶段 | 解析方式 |
|---|---:|---|
| TXT / Markdown | 是 | Python 原生文本解析 |
| PDF | 是 | Unstructured，Tika 兜底 |
| DOCX | 是 | Unstructured / python-docx |
| XLSX | 是 | openpyxl |
| PNG / JPG | 是 | EasyOCR，后续可换 PaddleOCR |
| PPTX / HTML | 第二阶段 | Unstructured |
| DOC / RTF / EML | 第二阶段 | Tika |
| DXF | 第二阶段 | ezdxf |
| DWG | 不直接支持 | 先通过 ODA 工具转换为 DXF |

## 7. 核心业务规则

### 7.1 文档入库

- 上传文件必须校验大小、扩展名、MIME 和文件签名。
- 服务端使用 UUID 保存文件，原始文件名只作为 metadata。
- 文件内容哈希相同且 ACL 相同时，默认判定为重复文档。
- 每个文档有 `document_id` 和递增的 `document_version`。
- 每个分块有稳定的 `chunk_id`。
- 新版本必须全部处理成功后才切换为 active。
- 失败任务可以安全重试，不产生重复向量。

### 7.2 Embedding

- 文档向量和查询向量必须使用同一 Provider、模型、维度和语义任务规则。
- 更换 Provider、模型或维度必须建立新 collection 并重新向量化。
- 不允许把不同模型生成的向量混入同一个 collection。
- Embedding 失败不得自动换另一家供应商继续写入当前索引。

### 7.3 检索与回答

- 检索必须包含 `tenant_id` 过滤。
- 普通用户只能访问本部门、公开内容和自身允许的敏感度。
- 默认召回 Top 20，按需 Rerank 到 Top 5。
- 相邻 chunk 可以合并，但必须保持引用映射。
- 相关度不足时直接拒答，不让 LLM 猜测。
- LLM 只能根据提供的参考片段回答。
- 回答中的每个来源都必须再次通过用户权限校验。

### 7.4 删除与审计

- 删除文档时同步删除原文件、所有版本向量和可识别缓存。
- 审计记录按合规要求保留，但不得保存 API Key。
- 所有云端调用记录实际 Provider、模型、发送的 chunk ID、耗时和结果。

## 8. API 范围

```text
POST   /v1/documents
GET    /v1/documents/:documentId
DELETE /v1/documents/:documentId
POST   /v1/documents/:documentId/reindex

GET    /v1/ingestion-jobs/:jobId

POST   /v1/knowledge/query

GET    /health/live
GET    /health/ready
GET    /metrics
```

上传接口返回 `jobId`，不等待大文件处理完成。查询接口返回：

```json
{
  "answer": "验收完成后 30 天内付款。[来源1]",
  "sources": [
    {
      "documentId": "uuid",
      "sourceName": "财务制度.pdf",
      "page": 12,
      "chunkId": "hash"
    }
  ],
  "traceId": "uuid",
  "provider": "deepseek",
  "model": "实际模型ID"
}
```

## 9. 非功能要求

### 9.1 安全

- 越权检索率必须为 0。
- confidential 默认零出网。
- 上传目录不可执行。
- 防止路径穿越、压缩炸弹和伪造 MIME。
- 主服务和 Worker 以非 root 用户运行。
- Python Worker 仅允许内网访问，不暴露公网。

### 9.2 可靠性

- 入库任务可重试、可恢复、幂等。
- 429、超时和部分 5xx 使用指数退避。
- 401、403 和参数错误不重试。
- Rerank 失败可退回向量排序。
- LLM 可配置备用 Provider；Embedding 不跨 Provider 自动降级。

### 9.3 可观测性

- 每个请求和任务有 trace ID。
- 记录 P50/P95 延迟、错误率、429、重试数、模型用量和成本。
- 记录解析耗时、队列长度、失败文档和磁盘使用率。
- 日志结构化输出，生产环境采集到集中日志系统。

### 9.4 可迁移性

- 所有路径、Provider、模型和限额均使用环境变量。
- Mac 和服务器使用相同容器与接口。
- 主服务通过接口访问 Chroma 和 Python Worker，不依赖进程内 Python。
- VectorStore 抽象允许后续切换 Qdrant/Milvus。

## 10. 验收标准

### 10.1 本地闭环验收

- 能在 Mac 上通过 Docker Compose 启动主服务、Python Worker、Redis 和 Chroma。
- 上传至少 5 份不同格式文档并成功入库。
- 能正确回答真实问题并返回文档与页码。
- 无答案问题能够明确拒答。
- 重复上传不会产生重复 chunk。
- 删除文档后无法再检索到其内容。

### 10.2 权限验收

- 财务用户能检索财务 internal 文档。
- 其他部门不能检索财务 internal 文档。
- 不同 tenant 之间无法互相检索。
- 客户端无法通过伪造角色取得额外权限。
- confidential 未获批准时不会调用 Embedding、Rerank 或 LLM。

### 10.3 Provider 验收

- 至少跑通一个 Embedding Provider 和一个 LLM Provider。
- Provider 通过配置切换，业务代码中无散落的供应商判断。
- 能分别配置“Alibaba Embedding + DeepSeek LLM”等组合。
- Provider 错误被转换为统一错误格式且不泄露 Key。

### 10.4 质量验收

- 建立至少 30 条真实问答评测集。
- 记录 Recall@K、引用正确率、无答案拒答率、P95 延迟和单次成本。
- 越权率为 0。
- 是否启用 Rerank 由评测结果决定。

## 12. 实施原则

1. 先跑通最小闭环，再扩展格式和供应商。
2. TypeScript 主服务不直接解析复杂文档。
3. Python Worker 不掌握用户身份、模型 Key 或向量库写权限。
4. 供应商差异封装在 Provider 层，不进入业务服务。
5. 安全过滤早于云端调用。
6. 每个功能必须同时具备成功路径、失败路径和权限测试。
7. 模型名称、价格和限流以上线时供应商官方控制台为准。
